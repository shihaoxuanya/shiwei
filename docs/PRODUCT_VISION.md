本文描述拾微最终要成为什么，以及未来产品和技术决策应遵守的方向，**不是当前版本的功能清单或开发授权**。

- 未经用户后续明确下达具体任务，不增加本文中的未来功能，不引入大型框架，不提前实现 GraphRAG、Agent、云同步或移动端。

## 2. 产品定位：优化 Recall，而不是 Storage

拾微是**个人 AI 记忆工具（Personal AI Memory）**。

> 帮用户记住过去看过的、写过的、做过的事情，在未来真正需要的时候重新想起来。

拾微不是传统笔记软件、文件管理器、Markdown 编辑器、Obsidian / Notion 替代品、PDF Chat、RAG Demo、ChatGPT 套壳或单纯的知识库。文件和笔记是信息入口，不是产品的终点。

用户已经有文件夹、网盘、微信、邮箱、浏览器收藏和各种笔记工具。真正的问题不是没有地方保存，而是：

> 我知道以前看过、写过、做过，但是需要的时候想不起来在哪里，也想不起具体内容。

典型提问包括：

- 我之前是不是处理过类似问题？上次那个项目最后怎么解决的？
- 黄总之前让我修改什么？
- 之前讨论 TiDB 迁移的会议是哪天？
- 我以前为什么没采用 ASM？那个数字是多少来着？
- 我什么时候第一次研究这个问题？我之前对此是什么观点？

用户不应为了使用拾微学习文件夹体系、标签、双链、Embedding、Chunk、RAG、向量数据库、知识图谱或提示词工程。这些属于内部实现。

用户应感知到的只有：**我把东西交给拾微，它替我记住；以后我忘了，直接问它。**

## 3. 核心闭环与成功体验

```text
现实中产生信息 → 交给拾微 → 自动理解和保存，无需主动整理
                                      ↓
时间过去，用户忘记 → 自然语言询问 → 找回过去并恢复上下文
                                      ↓
                              可靠回答 → 原始出处
```

真正的 Aha Moment 是：

> 我自己已经忘了，但它居然还记得。

不能明显增强这个闭环的功能，默认不是高优先级。评价产品首先看能否可靠找回个人经历与信息，而不是存储量、功能数量或内部技术复杂度。

## 4. 六项长期产品原则

### 不用整理

用户负责输入真实信息；系统承担理解、组织、索引和关系建立。不要要求用户长期维护复杂目录、标签、双链、知识图谱或笔记模板。

### 自然语言召回

允许“我之前开过一个会，是什么时候来着？”这样的模糊回忆，不要求用户记住文件名、标题、精确关键词或保存位置。精确搜索可以存在，但不应成为找回记忆的前提。

### 可靠优先于聪明

有可靠来源才回答；只有部分来源就明确不确定；没有可靠来源就说明“没有找到可靠记录”。绝不能把猜测当成用户过去真实发生过的事情。

回答明确区分 **Source Fact / Derived Inference / Unknown**。例如来源只写“单次迁移 38～50 天、至少两轮”，可以在“两轮完全串行、每轮耗时相同”的前提下推算 76～100 天，但必须标明这是计算推断，不是会议明确给出的项目总工期。数字、范围与原意均需保真。

### 重要回答可追溯

Citation 是核心能力，不是附属装饰。用户应能知道“为什么这样回答”，并回到原始文件、笔记、记录及对应上下文。来源事实与推断的边界不能被引用样式掩盖。

### 数据属于用户

> 你的记忆属于你，而不属于某一个模型。

长期必须支持原始数据导出、数据库备份、模型替换、Embedding 和索引重建。搜索索引不能成为唯一真相源，更换 GPT、DeepSeek、Claude 或本地模型不能使用户失去记忆。这是长期要求，不是对当前导出、恢复等能力已经实现的声明。

### Local First

在合理情况下，原始文件、笔记、个人记忆和索引均保存在本地。远程模型只获得当前请求必要的上下文；未来即使增加同步，也必须以用户数据控制权为先。

这一原则不应掩盖当前实现的实际网络边界：现有可选远程 Embedding 会发送待索引的派生文本，区别于聊天仅发送必要上下文。现状与长期目标的差异记录在审阅文档中；本文不更改现有配置、授权或模型链路。

## 5. 从 Document Memory 到 Personal Context

当前 MVP 围绕 `Source / Document / Chunk / Search` 构建，是正确的第一阶段。长期来看，Document 是信息来源，而不是最终的核心抽象。

未来需要逐渐理解：

```text
Person · Project · Event · Decision · Problem · Solution · Idea
Experience · Task · Place · Time · Source · Relation
```

例如，不只识别某份 DOCX 中出现“Oracle 数据库恢复”，而是能恢复“2026 年 8 月，某医院项目进行恢复测试，遇到问题，经过排查，做出决定，最终解决”的个人上下文。

这些是未来的概念方向，不是现在创建数据库表、知识图谱或引入新框架的要求。

## 6. 时间与变化

### 时间是一等公民

用户会问“上次、之前、第一次、最近、去年、三个月前、哪天、什么时候、后来、最后”。长期模型需要逐渐区分：

- `created_at`：记录创建时间。
- `updated_at`：记录更新时间。
- `event_time`：记录所描述的事件发生时间。
- `mentioned_time`：正文或标题明确提及的时间。
- `valid_from / valid_to`：信息适用的时间范围。

例如：2026-09-05 写下标题为“2025年9月3日会议”的笔记，标题描述的会议时间是 2025-09-03，不能用笔记创建时间替代。明确提及日期也不自动等于任意事件的日期；缺少确定依据时不得猜测。

现有 `mentioned_dates` 是阶段性基础，不意味着以上完整时间模型已经实现。

### 理解信息如何变化

如果记录依次是“1 月计划用 OGG → 3 月测试出现问题 → 5 月最终改用 TMS”，回答“最后用了什么？”时，应恢复决定的演变，而不是把 OGG、TMS 平铺为同等有效答案。

长期 Memory Consolidation 方向包括替代关系（supersede）、冲突（conflict）、修订（revision）、决定历史（decision history）、当前状态（current state）和过时记忆（stale memory）。**当前不提前实现复杂系统。**

## 7. 输入越来越轻，笔记保持简单

当前文件、文件夹和笔记是正确的 MVP 输入。未来可根据真实需求逐步扩展网页、截图、剪贴板、邮件、会议记录、音频、AI 对话历史、手机分享及浏览器内容。

方向是：用户在任何地方遇到值得留下的信息，都能低成本交给拾微。例如未来可能通过全局快捷键“记一下”，输入一句话即保存，不必进入复杂编辑器。这些入口不属于本轮任务。

Notes 是快速写入经历、决定、想法和信息的入口，不要发展为 Notion、Obsidian 或 Word。不要追求复杂排版、数据库视图、Canvas、插件、双链、模板市场或高级 Markdown 编辑。**快速记录比强大的编辑器更重要。**

## 8. 一个自然出口：问拾微

用户不应被迫区分搜索文件、搜索笔记、普通聊天、知识库聊天或 RAG 模式。主要出口保持为自然的“问拾微”。

系统内部判断是否需要个人记忆、时间范围、涉及的人物/项目/事件、应查哪些来源，以及是否有可靠证据。这可称为 Memory Routing，但用户不需要看见术语、检索分数或调试过程。

## 9. 克制的主动能力与简洁界面

未来 Active Recall 可以在当前任务与过去案例高度相关，或新旧决定有明确冲突时，轻量提醒“你之前遇到过类似情况”。必须同时满足：**高相关、高价值、低干扰**。不要频繁通知、无意义提醒或为了显得智能而打扰用户。

底层模型可以逐步丰富，UI 应越来越简单。未来可能采用“今天、问拾微、记录、资料、设置”，或合并部分页面；用户关心的是“这是我过去的什么东西”，不是内部属于 Document 还是 Note。

未来“今天”首页可能呈现最近记录、最近使用的项目、值得重新想起的内容、被更新的知识或存在冲突的信息，而不是 Worker 版本、协议版本、Vector / Chunk 数量。**这不是当前导航更名或首页改版任务**；现有 MVP 页面与交互继续保持。

## 10. 长期个人上下文层与产品价值

拾微长期不一定只存在于自己的 App，可逐步成为用户拥有的 **Personal Context Layer**，在获得明确授权后，通过 MCP、API 或 Local Service 向 GPT、Codex、Claude 等不同 AI 提供个人上下文。

未来接口可能包括 `search_memory`、`recall_event`、`find_project`、`get_source`、`find_related_experience`。这些仅是方向示例，不是现有接口或本轮待实现接口。

长期竞争价值不应依赖某个向量检索、RAG、Embedding 或 LLM 技术，而在于持续积累的 Personal Context：从一天的一点记录，到一年、五年的工作、学习、项目、决定和经验。形成“它知道我的过去”的价值，同时坚持可导出、可迁移，不用数据锁定制造黏性。

## 11. 分阶段验证，而不是一次实现

| 阶段 | 范围方向 | 要验证的问题 |
| --- | --- | --- |
| Stage 1：当前 | 文件与笔记 → 混合检索 → AI 回答 → Citation → 可靠拒答 | 我忘了，它能否帮我想起来？ |
| Stage 2 | 真实用户反馈、输入摩擦、检索可靠性、数据安全、安装体验、快速记录 | 用户是否愿意持续使用？ |
| Stage 3 | 按真实需求增加入口、时间和项目/事件理解、知识更新、Memory Consolidation | 能否从文件检索走向长期记忆？ |
| Stage 4 | 克制的 Active Recall、跨应用 Personal Context、MCP/API | 能否成为其他 AI 的个人记忆层？ |

阶段不是排期承诺，也不自动授权进入下一阶段。拾微目前仍处于 MVP / Early Validation。

## 12. 架构北极星：资产、索引与模型分离

> All architecture decisions should preserve the long-term separation between user-owned canonical memory, rebuildable indexes, and replaceable AI models.

```text
Original Data → Canonical Memory → Derived Index → Retrieval → Context → AI
```

- **用户长期资产**：Original Data 和 Canonical Memory，不能因索引重建或模型替换而丢失。
- **可重建派生数据**：Embedding、Vector Index、FTS Index、Cache，不得成为唯一真相源。
- **可替换能力**：GPT、DeepSeek、Claude、本地模型等，不应决定用户记忆的所有权或存续。

当前落地边界仍是 Tauri 2 + React/TypeScript + Python Worker，Python 是本地知识库唯一写入者，ModelGateway 隔离模型差异。本文不改变运行时边界。

**术语不能混同**：当前代码中的 `CanonicalDocument` / `parsed/` 是从原始文件或笔记真值生成的结构化解析投影，可以重建；它不因为名字包含 Canonical，就等同于未来包含稳定身份、来源依据与历史语义的用户长期 Canonical Memory。当前原始文件和笔记真值必须继续保留，不能倒过来让派生索引成为资产依据。未来如需引入新的记忆表示，应另行明确任务及迁移、恢复和验收边界。

## 13. 以后每次开发的决策门槛

开发前先回答：

1. 用户真实遇到了这个问题吗？
2. 它影响核心闭环吗？
3. 有没有证据证明需要这个功能？
4. 能否用更小的改动解决？

没有明确证据，默认不开发。每个新功能至少应满足以下一项，并仍需具体任务授权：

- A：降低用户交付信息的成本。
- B：提高未来找回信息的概率。
- C：提高回答可靠程度。
- D：帮助理解信息随时间的变化。
- E：让过去经验在当前任务中产生价值。
- F：加强用户对自己数据的控制权。

主要价值只是“看起来酷”的功能，默认不做。

## 14. 最终愿景

拾微最终不是一个存知识的地方，而是：

> 一个让用户过去的知识、经历和决定永远可以重新被调用的个人 AI 记忆基础设施。

期望用户的体验逐步从“它能找到以前的文件”，到“它记得我写过什么”，再到“它知道我之前做过什么”，最终形成：

> 很多东西我不用逼自己记住，因为拾微会替我留着。
